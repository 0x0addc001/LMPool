# Part 1 [The Review Report]

## Summary

本文提出 LMPool，通过全局 KV-aware routing 保持数据并行副本间的 prefix locality，并以成本模型控制直连 NVLink pair 上的 KV block copy 或 move，从而在可复用会话发生跨 GPU handoff 时降低重复 prefill。

## Strengths

1. 论文将 locality 和 fluidity 分为两个相互约束的系统问题。路由优先避免不必要的数据移动，transfer 只在预计节省的 prefill 成本覆盖通信和干扰成本时执行。这个分解比单纯追求 cache hit rate 或无条件迁移更符合在线推理的实际代价。

2. 系统实现具有较完整的安全边界。控制面维护版本化元数据，物理 KV block 仍由各 worker 独占管理，prepare--execute--publish--finalize 协议避免未完成副本提前进入路由视图。190 个 CPU 测试和一个硬件门控测试覆盖了 block 生命周期、过期快照、事务幂等性、进程恢复和 NCCL 数据一致性。

3. 实验没有隐藏负面结果。论文明确报告 routing 对 Qwen3-0.6B 的 TTFT 没有改善、memory-skew 和 load-skew 没有形成稳定 transfer 收益，并通过 routing-only、transfer-only 和完整系统的消融区分 cache reuse、请求分布和数据移动的作用。这种边界分析对后续系统设计有参考价值。

## Weaknesses (Critical)

未发现会直接推翻系统正确性或实验数据真实性的致命错误。以下问题主要限制主张的外部有效性和相对于现有系统的说服力，但对 MLSys 接收判断具有较高权重。

1. 核心端到端正面结果来自一个带精确 future-demand forecast 的合成 session-handoff workload。该 benchmark 在 warm-up 后预先向控制面提供 reuse phase 的 prefix demand，而论文没有评估在线热点预测器的准确率、提前量或误报成本。因此，4.4--7.4\% 的吞吐提升和 32.4--40.4\% 的 TTFT 降低证明了“已知未来复用时，路由和复制可以协同工作”，但尚不能证明系统能在未知生产流量中识别并实现同等机会。这是当前最主要的外部有效性问题。

2. 多 GPU 对比均为同一 Mini-vLLM 原型上的内部消融，没有与 vLLM prefix caching、SGLang RadixAttention、LMCache 或其他可运行的 prefix-aware serving policy 在相同模型、KV budget 和到达过程下比较。内部 baseline 对机制归因是公平的，但不足以支持相对于现有生产系统的竞争力判断。论文的 related work 很完整，evaluation 却没有把这些系统转化为可测的对照。

3. Transfer admission 是论文的核心决策，但成本模型缺少独立验证。固定 40~ms prior 是手工选择的保守设置，不是由 standalone pilot 或 held-out study 拟合得到；正文也没有比较 static bandwidth、piecewise-linear profile、profile+EWMA、no-gate 等策略。现有 microbenchmark 证明了数据路径及其吞吐，却不能证明成本模型正确接受了有利 plan 或拒绝了不利 plan。

4. 实验只覆盖一台机器、六张 RTX 3090、三个独立 NVLink pair 和两个小于 2B 且 KV geometry 相同的模型。256-token block 也明显大于常见 serving engine 的 page size。缺少 1/2/4/6 GPU scaling、较大模型、不同 KV geometry、较小 block size 和其他拓扑，使得控制面扩展性、碎片化代价和 transfer amortization 的普适性仍不明确。该问题不是实现正确性错误，但会显著限制 MLSys 评审对系统影响范围的判断。

## Rating

5/10。论文具有清晰的系统原则、可信的原型实现和诚实的消融结果，但当前正面证据依赖受控的 forecast-assisted workload，且缺少生产 trace、生产级 baseline 和成本模型有效性实验，因此更接近有潜力但证据尚未达到 MLSys 接收标准的 weak reject / borderline 工作。

# Part 2 [Strategic Advice]

## 问题根源

第一项弱点不是措辞问题，而是 workload 将最困难的热点发现环节作为外部输入。系统真正验证的是 forecast 之后的 placement、transaction 和 routing，而不是端到端的在线预测。第二项弱点源于原型以 Mini-vLLM 为统一实验底座，这有利于控制变量，但也把结论限制为内部机制增量。第三项弱点来自开发过程中先用 microbenchmark 描述 payload-dependent cost，再手工加入完整 serving transaction 的保守固定先验；这个流程可以形成可用策略，却没有形成审稿人可检查的预测准确率和决策消融。第四项弱点属于实验资源和实现范围限制，与论文表述无关。

## 可救性判断

Forecast 的来源、内部 baseline 的性质、256-token block 和六 GPU 范围都可以在修订期内通过收紧主张和补充 threats to validity 准确说明，但文字补救不能替代新证据。成本模型验证最容易通过补充实验解决，因为现有日志已经记录 estimated 和 observed cost，可以直接计算误差并重放 admission 决策。生产 trace 和生产级 serving baseline 的工作量更大，但至少需要其中一项才能显著提高接收概率。更大模型和拓扑扩展属于结构性实验缺口；如果当前硬件无法支持，应明确将论文定位为 scale-up prototype，而不是通用分布式 KV pool。

## 行动指南

首先，应在 ShareGPT 多轮会话、LMSYS-Chat-1M 的可重建会话或公开 agent trajectory 上重放真实 prefix popularity、reuse distance 和 session affinity。必须同时报告 forecast precision、recall、lead time、无效复制比例以及相对于 oracle forecast 的性能差距。没有预测器时，应将 session-handoff 结果明确写成受控上界实验。

其次，应至少加入一个生产级 engine baseline。最可操作的方案是在相同 Qwen3 模型、输出长度、KV budget 和到达 trace 下比较 vLLM prefix caching 的 round-robin 配置，并实现同等信息条件下的 prefix-aware routing；如果无法集成 Mooncake 或 LMCache，应解释接口和硬件限制，不能用 related-work 表代替实验。规模实验应报告 1/2/4/6 GPU throughput、TTFT、控制面消息率和决策延迟，并补充 16/64/256-token block 的敏感性。

再次，应增加成本模型消融。至少比较 no transfer、always transfer、fixed 4-block bandwidth、pair-specific piecewise-linear profile、profile+EWMA 五种策略，报告 predicted-versus-observed latency、MAE 或 P95 error、beneficial-plan acceptance、harmful-plan rejection 和最终吞吐/延迟。对 $\rho$、fixed residual 和 expected reuse 的敏感性可以直接说明收益来自正确决策，而不是 session-handoff workload 的人工构造。

最后，当前版本和 rebuttal 应主动限定攻击面。核心主张应表述为：LMPool 验证了 locality-aware routing 与 pair-local NVLink transfer 的可组合机制，并在 forecast-assisted handoff 中展示收益；论文不声称优于所有生产系统，也不声称 memory pressure 或 request skew 必然触发有利 transfer。应把 routing-only 在 Qwen3-0.6B 上与完整系统 E2E 置信区间重叠的结果保留在正文，以表明作者没有夸大 transfer 的增量作用。

# LMPool Oral Script: 10-Minute Version

## Slide 1: Title (0:00-0:20)

Good morning. I am Jialiang Li. I will present LMPool, a system that combines KV-aware routing with direct NVLink transfer. The central rule is simple: reuse local KV first, and move KV only when the whole transaction is worthwhile.

Pointer: title, then repository URL.

## Slide 2: The Placement Mismatch (0:20-1:00)

Prefix caching only saves work when a request reaches a GPU that still holds its prefix. With data parallel workers, round robin can miss that cache. Strict owner routing can overload one GPU. Moving KV without a benefit check can cost more than recomputation. LMPool treats request placement and KV placement as one scheduling problem.

Pointer: the two mismatch illustrations, then the design question.

## Slide 3: Two Principles (1:00-1:35)

Routing addresses cache locality. It sends a request toward a GPU with a useful ready prefix, but also accounts for queue and capacity pressure. Transfer addresses cache fluidity. It copies or moves a complete block chain only when placement no longer matches reusable demand. Routing comes first because avoiding a transfer is cheaper than accelerating one.

Pointer: blue routing box, then green transfer box.

## Slide 4: System Architecture (1:35-2:15)

LLMEngine accepts requests. The control plane stores global metadata such as prefix ownership, capacity, generation, and leases. Each GPU has a data-plane process with a Local Scheduler, Local Block Manager, Model Runner, and physical KV cache. The control plane sends only metadata. Model Runners exchange packed KV tensors directly over NVLink.

Pointer: LLMEngine, Global Scheduler, one data-plane process, then the green NVLink arrow.

## Slide 5: A Request Through LMPool (2:15-3:00)

The engine creates a Sequence and chained hashes for complete blocks. The router evaluates healthy ranks. The selected worker reuses ready blocks and allocates only the missing suffix. A genuine shortage can enter the foreground-transfer gate. The Model Runner performs prefill and decode. Only ready blocks are published, and reusable prefixes can remain in cache after completion.

Pointer: follow the numbered flow; pause at routing, transfer, and publication.

## Slide 6: KV-Aware Routing (3:00-3:45)

This cost estimates work on GPU (g). (R), (N), and (S) are request blocks, prompt tokens, and block size. (h_g) is the number of ready matching blocks. The unmatched suffix gives missing blocks (n_g) and missing prompt tokens (M_g). (F_g) measures free capacity, and (Q_g) is queued plus running work. I choose minimum estimated cost, not maximum cache-hit rate.

## Slide 7: Transactional KV Transfer (3:45-4:25)

Prepare locks the source chain and reserves destination capacity. Execute sends one packed tensor. Publish registers destination blocks as ready and visible to routing. Finalize keeps the source for a copy or reclaims it for a move. A failed transaction aborts without exposing partial destination state.

Pointer: Prepare, Execute, Publish, Finalize, then abort.

## Slide 8: Cost-Gated Transfer Admission (4:25-5:15)

The left branch maps plan bytes to a P95 latency profile measured separately for each NVLink pair and block-count bucket. The right branch learns nonnegative residuals from completed source operations and complete dispatch-to-publish transactions. These residuals use EWMAs, so recent observations influence the estimate without reacting to one noisy sample. Admission takes the conservative maximum of the profile and observations. It proceeds only when saved prefill work exceeds (
ho T_{mathrm{xfer}}), and source generation, pair topology, and destination capacity remain valid.

Pointer: measured profile, online observations, maximum, then admit or reject.

## Slide 9: Evaluation Design (5:15-5:45)

I evaluate six RTX 3090 GPUs, arranged as three direct NVLink pairs, with Qwen3-0.6B and Qwen3-1.7B. Every policy has the same per-worker KV budget. Each result is the mean of five fixed-seed trials. The three workloads isolate long-prefix locality, load-skew background placement, and memory-skew foreground release. These are controlled internal studies, not production traces.

Pointer: hardware, workload rows, then scope.

## Slide 10: Routing Results (5:45-6:30)

This chart shows why prefix length matters. At 5x shared-prefix length, routing cuts uncached prefill by about 60 percent. On 0.6B, throughput rises 11.8 percent, TTFT falls 18.6 percent, and P90 E2E falls 21.1 percent. On 1.7B, the gains are 21.3, 25.2, and 25.6 percent. The request distribution remains balanced, so the gain comes from avoided prefill rather than concentrating work at one owner.

Pointer: the 5x bars for 0.6B, then 1.7B.

## Slide 11: NVLink Data-Path Calibration (6:30-7:00)

This is a direct transfer microbenchmark across all three physical pairs and both models. It validates payload correctness and measures P95 transfer latency from one to 64 blocks. Larger plans amortize fixed overhead, so bandwidth rises with payload. The curves initialize the transfer-cost model. They prove the data path, not an end-to-end serving speedup.

Pointer: block-count axis, the two model curves, then validation note.

## Slide 12: Transfer Results and Boundary (7:00-8:15)

The left panel is load skew. The system executes three background placements, copies 87 blocks, and placement leases route 95 later requests. TTFT falls substantially because later requests find reusable KV. However, decode scheduling raises TPOT, so mean E2E and throughput do not improve uniformly. The right panel is memory skew. On 0.6B, foreground transfer safely releases 35 source blocks. The result remains statistically close to routing-only. On 1.7B, the full offload verification predicate is not met. These outcomes are useful boundaries: transfer can execute correctly without automatically improving every serving metric.

Pointer: left panel mechanisms, then right panel release boundary.

## Slide 13: Limitations and Future Work (8:15-9:00)

The workloads are synthetic and replayed deterministically. The study uses internal baselines, six consumer GPUs, two sub-2B models, and one block size. The cost model has pair-specific profiles and online residuals, but I have not yet reported held-out prediction error or a sensitivity study of the admission policy. The control plane can rebuild metadata from workers, but it has no replicated consensus or launcher failover.

Pointer: scope, cost-model evidence, availability.

## Slide 14: Takeaways (9:00-9:35)

Routing solves cache locality by avoiding repeated prefill where a ready prefix already exists. Direct NVLink transfer provides cache fluidity when the data should be placed elsewhere. The transfer mechanisms are verified: background copies, placement leases, and safe source-block release all execute. The final result is deliberately qualified: a completed transfer is not, by itself, a universal throughput or mean-E2E improvement.

Pointer: each takeaway, then the final sentence.

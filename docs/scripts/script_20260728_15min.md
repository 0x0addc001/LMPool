# LMPool Oral Script: 15-Minute Version

This version follows the slide deck and adds technical detail for a slower presentation. The timing is approximate and assumes a non-native English speaking rate.

## Slides 1--3: Problem and Principles (0:00--2:20)

Good morning. I am Jialiang Li. This talk presents LMPool, a KV-cache pool for data-parallel LLM serving. Prefix caching saves prefill only when the request reaches a GPU that still has the prefix. Independent workers therefore create a placement mismatch: round robin misses useful KV, strict owner routing can create a hotspot, and unconditional movement can cost more than recomputation.

LMPool has two principles. KV-aware routing addresses cache locality. It selects a rank with useful ready blocks while considering queue and capacity pressure. NVLink transfer addresses cache fluidity. It changes KV placement only when a completed transaction is likely to save more prefill work than it costs. The order matters: when routing can use existing KV safely, there is no reason to transfer it.

Pointer: Slides 1--3, title, mismatch illustration, then the blue and green principle boxes.

## Slide 4: Architecture (2:20--3:30)

LLMEngine owns request admission and receives worker results. A single control-plane process keeps global metadata: prefix locations, capacities, generations, transfer states, and placement leases. Each GPU has a separate data-plane process. It contains a Local Scheduler, Local Block Manager, Model Runner, and the physical KV cache. The control plane does not relay KV tensors. It sends compact scheduling messages. Model Runners transfer one packed tensor directly between GPUs through NCCL point-to-point communication on an NVLink pair.

## Slides 5--7: Routing, Lifecycle, and Safety (3:30--5:30)

At ingress, LLMEngine creates a Sequence and chained hashes for its complete KV blocks. The Global Scheduler queries the global metadata and scores healthy ranks. A worker reuses only published ready blocks. It allocates and computes the missing suffix locally. If it cannot allocate enough blocks, it can request foreground transfer.

The routing cost combines three terms. The first is uncached work after the longest local ready prefix. The second is reclaim pressure from limited free blocks. The third is queued and running work. This avoids treating a cache hit as automatically better than a lightly loaded rank.

Transfer is transactional. Prepare validates source generation and reserves target capacity. Execute packs the selected block chain and sends it. Publish installs destination metadata only after the blocks are ready. Finalize either retains the source for a copy or reclaims it for a move. Abort removes reservations and preserves the source. This prepare--publish boundary prevents readers from seeing partial state.

Pointer: request flow, routing formula, then transaction lifecycle.

## Slide 8: Cost Model (5:30--6:40)

The admission gate estimates the cost of the entire transfer, not just tensor bandwidth. First, it maps the planned number of blocks to payload bytes and obtains a pair-specific P95 latency from a measured profile. The profile contains one, two, four, eight, sixteen, thirty-two, and sixty-four block points; intermediate plan sizes use piecewise-linear interpolation.

The system also learns two nonnegative residual EWMAs for each pair and size bucket. A source observation records the actual source-side transaction time beyond the data-path profile. A dispatch-to-publish observation records the complete placement interval beyond the static estimate. Taking the maximum of the profile estimate and online estimates is conservative without double counting overlapping time. The plan is admitted only when predicted saved prefill work exceeds the configured safety ratio times the transfer estimate, and all source, pair, and target checks still hold.

Pointer: profile branch, observation branch, maximum, and admission diamond.

## Slide 9: Evaluation Design (6:40--7:30)

The study uses six RTX 3090 GPUs arranged as three NVLink pairs, Qwen3-0.6B and Qwen3-1.7B, equal per-worker KV budgets, fixed seed, EOS disabled, and five trials. Routing uses 1x, 3x, and 5x shared prefixes and 64 output tokens. Load skew uses three shared groups, a narrow hot set, and 8-token outputs to expose placement overhead. Memory skew uses six groups, a late pressure phase, and 16-token outputs to exercise foreground release. These are deterministic mechanism studies, not a claim about production traces.

Pointer: table rows and scope.

## Slide 10: Routing Results (7:30--9:00)

The routing chart is the strongest end-to-end result. At 5x shared-prefix length, request-level shared-prefix exposure is 91.7 percent. On Qwen3-0.6B, uncached prefill falls from 884,997 to 354,821 tokens. Throughput rises from 43.6 to 48.8 tokens per second, TTFT falls from 536 to 436 milliseconds, and P90 E2E falls from 3,977 to 3,140 milliseconds. On Qwen3-1.7B, uncached prefill falls from 885,816 to 345,605 tokens. Throughput rises from 38.2 to 46.4 tokens per second, TTFT falls from 691 to 517 milliseconds, and P90 E2E falls from 4,903 to 3,649 milliseconds.

The important point is that routing does not achieve this by pinning requests to a single owner. The routing score still accounts for queue and capacity. The remaining gain is avoided prefill work.

Pointer: 5x bars for both models and the uncached-prefill annotation.

## Slide 11: Transfer Microbenchmark (9:00--9:50)

The transfer microbenchmark validates the data path separately. It measures P95 latency across every physical pair, both model geometries, and one through sixty-four blocks. Every destination validates the copied bytes. This establishes the payload-dependent part of the cost model. It does not include queueing, later request demand, or model interference, so it is not presented as a serving result.

Pointer: profile curves and the validation note.

## Slide 12: Load and Memory Skew (9:50--12:10)

The load-skew panel confirms that background placement executes. In both models, three placements copy 87 blocks, and placement leases route 95 later requests. For 0.6B, LMPool reduces mean TTFT from 507 milliseconds for round robin to 237 milliseconds. For 1.7B, it reduces mean TTFT from 725 to 247 milliseconds. It also reduces uncached prefill substantially. However, mean TPOT is higher in the full system, so throughput and mean E2E are not uniformly better. This is evidence for the mechanism and its scheduling trade-off, not a universal performance claim.

The memory-skew panel exercises foreground move and release. At 0.6B, transfer-only completes three foreground plans and releases 35 source blocks. Full LMPool is close to routing-only on throughput and latency. At 1.7B, the full offload verification predicate is not satisfied. This result shows safe execution but not a repeatable end-to-end offload speedup.

Pointer: load panel first, then memory panel and the boundary note.

## Slides 13--15: Limits, Takeaways, and Thanks (12:10--15:00)

The limitations are material. The inputs are synthetic and deterministic. The study uses internal baselines, six consumer GPUs, two sub-2B models, and one 256-token block size. The cost model has empirical pair profiles and online residuals, but no held-out cost-prediction error or sensitivity study. The control plane has recovery from fresh worker snapshots but no consensus protocol or launcher failover.

The takeaways are therefore bounded. KV-aware routing has stable long-prefix benefits. NVLink transfer, background placement, leases, and safe source release are implemented and exercised. Yet a completed transfer is not enough to guarantee an E2E or throughput gain. Future work should evaluate online demand prediction, public production traces, larger model and topology ranges, and held-out admission-model evaluation.

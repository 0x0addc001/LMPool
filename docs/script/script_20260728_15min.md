# LMPool Oral Script: 15-Minute Version

## Slide 1: Title (0:00-0:25)

Good morning. I am Jialiang Li. Today I will present LMPool, a multi-GPU LLM serving system that
coordinates locality-aware request routing with direct NVLink KV-cache
transfer. The central idea is simple: route a request to reusable KV when
possible, and move KV only when expected future reuse can repay the complete
transfer transaction.

Pointer: title, subtitle, repository URL.

## Slide 2: The Placement Mismatch (0:25-1:20)

Prefix caching works naturally inside one inference engine because request
execution and cached KV share one allocator. Data-parallel serving breaks this
assumption. As the two boxes on the left show, each GPU owns an independent
allocator and physical KV cache, but ingress assigns requests globally.
Round robin can send a matching request away from its prefix and force
repeated prefill. Strict owner routing is not sufficient either, because a hot
prefix can turn one owner into a queueing hotspot. Unconditional movement is
also wrong because synchronization and model interference can cost more than
local recomputation. LMPool addresses this placement mismatch.

Pointer: left assumptions, right failure modes, bottom question.

## Slide 3: Two Principles (1:20-2:05)

The left principle addresses cache locality. A request should use a GPU with a
useful contiguous prefix, but locality must be balanced against queue and
capacity pressure. The right principle addresses cache fluidity. A complete
KV chain may be copied or moved when future demand no longer matches current
placement. This does not solve every form of request skew. It specifically
changes where reusable KV is available. Routing is considered first because
avoiding a transfer is cheaper than optimizing one. Transfer is admitted only
when measured data-path cost, transaction overhead, and expected reuse support
it.

Pointer: blue routing principle, green transfer principle, center objective.

## Slide 4: System Architecture (2:05-3:00)

The architecture has one main process, one control-plane process, and one
data-plane process per GPU. LLMEngine owns ingress and completion aggregation.
Global Scheduler and Global Block Manager store versioned prefix, load, and
capacity metadata. They do not own physical KV. Each worker owns Local
Scheduler, Local Block Manager, Model Runner, and its CUDA allocation. The
Local Block Manager is authoritative for physical block IDs, readiness,
references, and generations. Model Runners exchange packed KV tensors only
across configured direct NVLink pairs. This separation coordinates a logical
pool without pretending that HBM is shared memory.

Pointer: trace control flow downward; trace metadata upward; finish at the
green NVLink path.

## Slide 5: A Request Through LMPool (3:00-4:10)

I will walk through one request using the numbered list. LLMEngine tokenizes
the prompt, creates a Sequence, and computes chained hashes for complete prompt
blocks. A new ingress request uses requester rank minus one, meaning that it
has no local GPU yet, so Global Scheduler considers every healthy replica. It
finds the longest contiguous ready prefix on each candidate, combines this
with queue and capacity metadata, reserves one rank, and returns the
destination. The target worker reuses ready local blocks and allocates missing
blocks. Only a real shortage may enter the foreground transfer gate. Model
Runner executes prefill and decode. The worker then publishes a newer
versioned snapshot. Only ready, committed blocks become globally visible.
When the request completes, references are released, while reusable complete
prefixes may remain cached.

Pointer: pause at Global route, Optional foreground transfer, and Publication.

## Slide 6: KV-Aware Routing (4:10-5:15)

The four formula lines estimate token-equivalent work for candidate GPU \(g\).
On the right, \(R\) is the required prompt-block count, \(N\) is the prompt
length, and \(S\) is tokens per block. The longest contiguous ready match is
\(h_g\), so \(n_g\) is the number of missing blocks. \(M_g\) converts that
missing region back to prompt tokens, capped by the real prompt length.
\(F_g\) is currently free capacity, and \(A_g\) is the missing block count
beyond that free capacity, which represents reclamation pressure. \(Q_g\)
summarizes queued, pending, and running work. The weights \(w_p\) and \(w_e\)
price prefill and reclamation in the same token-equivalent unit.

The minimum-cost feasible rank wins. A prefix owner can still be bypassed when
its load is sufficiently higher and additional missing-prefill work stays
within the bounded-spill threshold. Transfer is a separate cost-gated action;
ordinary spill does not silently include a transfer.

Pointer: formula line and matching definition, then Decision and Bounded
spill.

## Slide 7: Transactional KV Transfer (5:15-6:10)

Transfer follows prepare, execute, publish, and finalize. Prepare locks the
source identity and reserves concrete destination blocks without exposing a
replica. Execute gathers source blocks into one packed tensor, issues matching
NCCL point-to-point operations, and scatters into the reserved destination.
Publish registers the destination blocks as ready and submits a new snapshot.
This is the visibility boundary: receive completion alone is not enough.
Finalize either retains the source for copy semantics or releases a
dependency-safe, unreferenced suffix for move semantics. If any earlier phase
fails, abort preserves the source and releases the destination reservation.

Pointer: trace the main path, then the abort path.

## Slide 8: Cost-Gated Transfer Admission (6:10-7:20)

The top box describes a candidate with \(B\) blocks and payload \(X\). In the
left branch, the payload is matched to a pair-specific P95 profile measured at
one, two, four, eight, sixteen, thirty-two, and sixty-four blocks. Values
between these points use piecewise-linear interpolation. The paper setting
uses a 40-millisecond manual fixed prior plus 1.2 times the payload-dependent
profile term.

The right branch learns two nonnegative EWMAs for each NVLink pair and
power-of-two size bucket. A source observation measures the completed
source-side execution and stores its residual over the data-path profile. A
placement observation measures the longer dispatch-to-publish interval and
stores its residual over the static estimate. Nonnegative residuals prevent a
single unusually fast sample from making admission more aggressive.

The center takes the maximum of the static estimate and the two observed
estimates. This selects the conservative candidate without adding overlapping
intervals twice. At the bottom, foreground and background plans estimate saved
prefill differently, but both require saved work to exceed
\(\rho T_{\mathrm{xfer}}\). Source hash and generation, direct-pair topology,
target capacity, and pair availability are revalidated before execution.

Pointer: candidate, offline prior, online observations, conservative maximum,
saved-work branches, admit/reject diamond.

## Slide 9: Evaluation Design (7:20-8:00)

I evaluate six RTX 3090 GPUs arranged as three direct NVLink pairs. I use
Qwen3-0.6B and Qwen3-1.7B in BF16, hold the per-worker KV budget constant
across policies, run five trials with seed zero, and force 64 output tokens.
The locality workload isolates routing. Load skew tests a hot prefix that
round robin can replicate naturally. Memory skew tests foreground shortage
admission. Session handoff tests forecast-assisted background placement.
These are controlled internal ablations, not production-engine comparisons.

Pointer: hardware, workload table, Scope.

## Slide 10: Routing Cuts Uncached Prefill (8:00-8:55)

Routing raises cached-token coverage from 44.1 percent to 72.2 percent for
0.6B and to 71.3 percent for 1.7B. Uncached prefill falls by 50.2 and 48.6
percent. Per-rank request counts remain nearly uniform, so this is not achieved
by collapsing demand onto one owner. The latency effect differs. For 0.6B,
mean TTFT rises by 7.4 percent even though prefill work falls. For 1.7B, mean
TTFT falls by 10.2 percent. Both models transfer the same bytes per KV block,
but avoided prefill is more expensive for 1.7B. I therefore claim compute
reduction and a model-dependent latency payoff, not universal speedup.

Pointer: four table rows, then the three conclusion bullets.

## Slide 11: NVLink Data-Path Calibration (8:55-9:40)

The table now reports every measured plan size. The ranges cover two model
paths and all three physical NVLink pairs. One block moves 0.027 GiB and
achieves roughly 7.5 to 9.2 GiB per second. At eight blocks, bandwidth reaches
26.9 to 30.1 GiB per second. At 64 blocks, it reaches about 36.5 GiB per
second. Payload grows by 64 times, while bandwidth rises because launch,
gather, synchronization, and scatter overhead are amortized. Every destination passes
byte-for-byte validation. These measurements initialize the data-path profile;
they do not include serving queueing, future reuse, or model interference.

Pointer: Blocks, Payload, Bandwidth, validation note, Interpretation.

## Slide 12: Forecast-Assisted Session Handoff (9:40-10:40)

The left side shows the two-phase construction. I create 32 distinct long
prefix groups named by the benchmark. Each shared prefix repeats the base text
16 times and receives a short request suffix. During warm-up, one request from
each group is pinned to the source side of one of the three logical pairs:
ranks 0, 2, and 4. When all 32 complete, each group has one source-resident
ready chain.

The benchmark has already generated the following 96 reuse requests, so it can
count exact future prefix demand. The placement flow on the right checks
hotness, replica need, pair state, target space, batching, and benefit. It
admits three pair-level plans that copy 224 blocks. After commit, placement
leases divide the known reuse quota between source and replica. This proves
the mechanism under an accurate forecast; it does not evaluate an online
predictor.

Pointer: three left phases, right decision flow, bottom Scope.

## Slide 13: End-to-End Handoff Results (10:40-11:35)

Relative to round robin, full LMPool improves throughput by 4.4 percent for
Qwen3-0.6B and 7.4 percent for Qwen3-1.7B. Mean TTFT is 32.4 and 40.4 percent
lower, and mean E2E is 9.3 and 12.9 percent lower. Transfer-only reaches the
same 70.5 percent cached-token coverage, but 0.6B throughput is unchanged and
the 1.7B gain is only 3.2 percent. This ablation separates data placement from
request placement: copied KV has no service value unless later requests use
the new replica.

Pointer: compare policies vertically, then the three bold ranges.

## Slide 14: Why Routing and Transfer Must Cooperate (11:35-12:25)

The per-rank data explain the difference. Round robin and transfer-only retain
a 3.3 maximum-to-minimum submitted-request ratio. Their mean GPU utilization
stays around 31 to 35 percent. Full LMPool keeps the same cached-token ratio as
transfer-only, but placement-lease routing lowers the request ratio to 1.8 and
raises mean utilization above 50 percent. Compared with routing-only, full
LMPool adds 2.6 to 3.8 percent throughput. For 0.6B, routing-only and full
LMPool have overlapping mean-E2E confidence intervals, so the incremental
transfer claim is stronger for throughput and for the more compute-intensive
model.

Pointer: table rows, then the confidence-interval qualification.

## Slide 15: Where Transfer Does Not Help (12:25-13:15)

Memory pressure does not automatically create a profitable transfer. A valid
source chain, direct target with capacity, and enough future reuse must exist
together. In the 1.7B memory-skew workload, the gate accepts no transfer and
full-system throughput is slightly below round robin. Under steady load skew,
round robin quickly warms the same hot prefix on all six workers, so all
multi-GPU throughput results stay within 0.6 percent of baseline. These
negative results define the rejection boundary rather than proving a
speedup.

Pointer: memory-skew box, load-skew box, caution sentence.

## Slide 16: Limitations and Future Work (13:15-14:20)

The positive handoff result uses exact future demand, so I have not evaluated
the precision, recall, lead time, or invalid-copy rate of an online forecast.
The baselines are internal, and the study covers six consumer GPUs, two
sub-two-billion-parameter models with identical KV geometry, and one
256-token block size.

Held-out prediction error means calibrating the cost model on one set of plans
and measuring predicted versus observed cost on independent plans. I have not
reported that error. Cost-policy sensitivity means varying the 40-millisecond
prior, EWMA, safety ratio, and no-gate policy and observing transfer acceptance,
throughput, and latency. I have not completed that ablation either.

The control process can restart and rebuild global metadata from fresh worker
snapshots, but it does not implement replicated consensus. The launcher is
also a single point of failure. Future work therefore needs a public
multi-turn trace with an online predictor, a production serving baseline,
model/GPU/block-size scaling, held-out cost evaluation, policy ablations, and
replicated control and launcher recovery.

Pointer: scope bullets, cost-model bullet, availability bullet, Next
evaluation box.

## Slide 17: Takeaways (14:20-14:50)

The conclusion is not that KV should always move. Routing addresses cache
locality by reusing state where it already exists without creating a load
hotspot. Direct NVLink transfer provides cache fluidity when placement no
longer matches known demand. The mechanisms must cooperate because copied KV
matters only when routing sends demand to the replica. Finally, the rejection
boundary is part of the result: memory or request skew alone does not justify
movement. Route when possible. Transfer when profitable.

Pointer: four takeaways, then the green sentence.

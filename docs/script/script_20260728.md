# LMPool MLSys Oral Script

This script targets a 15-minute oral presentation. The spoken text is in English. The Chinese notes identify the delivery goal and the point that should not be overstated.

## Slide 1: Title (0:00--0:25)

Good morning. I am Jialiang Li from the Hong Kong University of Science and Technology. Today I will present LMPool, a multi-GPU LLM serving prototype that coordinates locality-aware request routing with direct NVLink KV-cache transfer. The key idea is simple: route a request to reusable KV when possible, and move KV only when the expected future reuse can repay the full transfer transaction.

讲解提示：开场只给出问题和一句话原则，不展开实现细节。

## Slide 2: The Placement Mismatch (0:25--1:20)

Prefix caching is effective inside one inference engine because the request and its cached KV state share the same allocator. Data-parallel serving breaks this assumption. Each GPU owns an independent cache, while a cluster-level ingress chooses where each request runs. Round robin can therefore send a request away from its reusable prefix and force repeated prefill. Always routing to the first owner is not sufficient either, because a hot prefix can turn one GPU into a queueing hotspot. Finally, moving every matching prefix is also wrong: communication, synchronization, and memory interference can cost more than recomputation. This placement mismatch is the problem addressed by LMPool.

讲解提示：清楚区分三种失败策略：round robin、strict owner routing、unconditional transfer。

## Slide 3: Two Principles (1:20--2:05)

LMPool separates the problem into two principles. The routing principle addresses cache locality. It asks whether executing on a prefix owner saves enough prefill work to justify its current queue and capacity pressure. The transfer principle addresses cache fluidity. It asks whether complete KV block chains should move to another GPU because placement no longer matches future demand. Routing is considered first because avoiding a transfer is cheaper than optimizing one. Transfer is admitted only when measured data-path cost, transaction overhead, and expected reuse support it.

讲解提示：不要把 fluidity 说成解决所有 request skew；它解决的是 KV placement 与 demand 不匹配。

## Slide 4: System Architecture (2:05--3:05)

The architecture has one main process, one control-plane process, and one data-plane process per GPU. LLMEngine owns request ingress and completion aggregation. The control plane contains Global Scheduler and Global Block Manager. It stores versioned metadata, not physical KV tensors. Each worker owns a Local Scheduler, Local Block Manager, Model Runner, and CUDA device. Local block managers are authoritative for allocation, readiness, reference counts, and physical block IDs. Model runners exchange packed KV tensors only across configured NVLink pairs. This separation lets the control plane coordinate a logical pool without pretending that HBM is physically shared memory.

讲解提示：强调 control plane 只管 metadata；KV tensor 不经过 control plane。

## Slide 5: A Request Through LMPool (3:05--4:15)

Let me walk through one request. LLMEngine tokenizes the prompt, creates a Sequence, and computes chained hashes for complete prompt blocks. Because an ingress request has no initial GPU, Global Scheduler considers every healthy replica. It finds the longest contiguous ready prefix on each candidate, combines this with queue and capacity metadata, reserves one rank, and returns that destination. The worker then reuses local ready blocks and allocates the missing blocks. A real local shortage may trigger a foreground transfer request, but only if the cost gate accepts a feasible plan. Model Runner performs prefill and decode. Ready KV state and load changes are published back as a versioned snapshot. When the request finishes, references are released, while complete prefixes can remain cached for later reuse.

讲解提示：这是最容易被问的完整流程。务必说“入口候选是所有健康 GPU”，不要误说只看 NVLink partner。

## Slide 6: KV-Aware Routing (4:15--5:10)

For each candidate, the router computes three quantities. The number of new blocks is the request block count minus the contiguous prefix match. Missing prefill is a block-rounded token estimate. Reclamation pressure measures how many required blocks exceed current free capacity. These terms are combined with queued, pending, and active decode work in one token-equivalent cost. The router chooses the lowest feasible cost, not the highest hit rate. A bounded spill can bypass a prefix owner when the load difference is large and the additional recomputation remains limited. In our locality workload, this policy roughly doubles useful cached-token coverage without concentrating all requests on one rank.

讲解提示：公式只解释物理意义，不逐个念权重。

## Slide 7: Transactional KV Transfer (5:10--6:05)

Transfer follows four phases. Prepare reserves concrete destination block IDs and locks the plan without making the new replica visible. Execute gathers the source blocks into one packed tensor, performs matching NCCL point-to-point operations, and scatters the received tensor into reserved blocks. Publish marks the destination blocks ready and sends a new snapshot. Finalize either keeps the source for copy semantics or releases a dependency-safe unreferenced suffix for move semantics. If any phase fails, abort preserves the source and releases the destination reservation. This ordering prevents routing from observing data that has arrived but is not yet registered as valid KV state.

讲解提示：回答并发安全时回到“visibility boundary is publication”。

## Slide 8: Cost-Gated Transfer Admission (6:05--7:10)

The transfer estimate starts from a measured P95 latency curve for each NVLink pair and payload size. The paper configuration adds a conservative 40-millisecond full-transaction prior and multiplies the payload-dependent profile term by 1.2. This 40-millisecond value is a manual cold-start setting, not a fitted standalone-pilot result. Completed source and placement transactions update separate nonnegative EWMAs by pair and size bucket. Admission takes the maximum of the static and observed estimates. A plan proceeds only when expected saved prefill exceeds this cost by the configured safety ratio and source generations and target capacity are still valid.

讲解提示：主动澄清 40 ms，避免被质疑 calibration provenance。不要说“我们测出 residual 正好是 40 ms”。

## Slide 9: Evaluation Design (7:10--7:55)

We evaluate on six RTX 3090 GPUs arranged as three direct NVLink pairs. We use Qwen3-0.6B and Qwen3-1.7B in BF16, keep the KV budget equal across multi-GPU policies, run five trials, and force 64 output tokens. Four synthetic workloads isolate different mechanisms. Locality tests routing, load skew tests a naturally replicated hot prefix, memory skew tests foreground shortage admission, and session handoff tests forecast-assisted background placement. These are controlled Mini-vLLM ablations. They do not establish superiority over a production vLLM or SGLang deployment.

讲解提示：主动承认 scope，避免在 Q&A 中被动防守。

## Slide 10: Routing Cuts Uncached Prefill (7:55--8:55)

Routing increases the cached-token ratio from about 44 percent to 72 percent for both models. This reduces uncached prefill tokens by 50.2 percent for Qwen3-0.6B and 48.6 percent for Qwen3-1.7B. Request counts remain nearly uniform across ranks, so this is not achieved by collapsing demand onto one owner. The latency response is model dependent. For 0.6B, TTFT increases by 7.4 percent even though prefill work falls. For 1.7B, TTFT decreases by 10.2 percent. The larger model makes each avoided prefill token more expensive, so the same locality improvement produces a clearer latency payoff. We therefore claim compute reduction, not universal latency improvement.

讲解提示：负面结果必须主动讲，体现严谨。

## Slide 11: NVLink Data-Path Calibration (8:55--9:40)

The transfer microbenchmark moves the K and V tensors of all layers and validates the destination byte for byte. Four blocks contain 0.109 GiB and achieve 20.5 to 23.1 GiB per second. Doubling the payload to eight blocks increases latency by only about 53 percent and raises bandwidth to 26.8 to 30.1 GiB per second. Mean bandwidth reaches 36.5 GiB per second at 64 blocks. This sublinear latency growth is why batching matters. The microbenchmark validates and initializes the data-path model, but it does not by itself prove that a serving transfer is beneficial.

讲解提示：microbenchmark 的主张是“数据路径与成本先验”，不是端到端提升。

## Slide 12: Forecast-Assisted Session Handoff (9:40--10:35)

The positive end-to-end workload has two phases. First, 32 long session prefixes are created on source GPUs. Before the reuse phase, the benchmark supplies the exact prefix demand of 96 queued requests. LMPool then copies 224 hot blocks in three pair-level plans. Placement leases distribute reuse requests across both source and destination replicas. This is an opportunity study under an accurate forecast. It proves that routing and transfer can compose when reuse is known early enough. It does not evaluate how accurately a production system can predict that reuse.

讲解提示：明确这是 forecast-assisted，不要称为 learned predictor。

## Slide 13: End-to-End Handoff Results (10:35--11:35)

Relative to round robin, the full system improves throughput by 4.4 percent for Qwen3-0.6B and 7.4 percent for Qwen3-1.7B. Mean TTFT falls by 32.4 and 40.4 percent, and mean end-to-end latency falls by 9.3 and 12.9 percent. Transfer-only increases cached-token coverage to the same 70.5 percent, but its 0.6B throughput is unchanged and its 1.7B gain is only 3.2 percent. This separation tells us that placing KV at another GPU is not enough; requests must also be routed to use the new replica.

讲解提示：先报 full vs baseline，再用 transfer-only 引到下一页的机制解释。

## Slide 14: Why Routing and Transfer Must Cooperate (11:35--12:30)

The per-rank data explain the difference. Round robin and transfer-only both retain a 3.3 ratio between the most and least loaded ranks. Their mean GPU utilization remains around 31 to 35 percent. Full LMPool keeps the same 70.5 percent cached-token ratio as transfer-only, but placement-lease routing lowers the rank request ratio to 1.8 and raises mean GPU utilization above 50 percent. Compared with routing-only, transfer adds 2.6 to 3.8 percent throughput. However, for Qwen3-0.6B, routing-only and full LMPool have overlapping end-to-end confidence intervals. The incremental transfer claim is therefore strongest for throughput and for the more compute-intensive model.

讲解提示：这是消融的核心页。不要说 full 在所有指标显著优于 routing-only。

## Slide 15: Where Transfer Does Not Help (12:30--13:20)

Memory pressure does not automatically make transfer useful. In the 1.7B memory-skew workload, the admission policy accepts no transfer, and full-system throughput is slightly below round robin. Under steady load skew, round robin quickly warms the same hot prefix on all six workers, so routing and transfer remove no additional work and all multi-GPU throughput results remain within 0.6 percent. These are not failed experiments. They define the admission boundary: transferable KV must be reusable, the target must have capacity, and future demand must be large enough to repay the transaction.

讲解提示：把 negative results 解释为 policy boundary，但不要把性能下降包装成优势。

## Slide 16: Limitations and Future Work (13:20--14:20)

The current evidence is deliberately bounded. The workloads are synthetic, and the positive handoff workload receives an exact forecast. Baselines are internal Mini-vLLM ablations. We evaluate six consumer GPUs, two sub-2B models with identical KV geometry, and one 256-token block size. The 40-millisecond transaction prior is manual, and we do not yet report held-out prediction error or a cost-policy sensitivity study. Finally, the control process can restart from worker snapshots, but there is no consensus or launcher failover. The next evaluation should add an online predictor on public multi-turn traces, a production serving baseline, model and block-size scaling, and cost-model prediction and admission ablations.

讲解提示：这一页用于建立可信度。口头报告不要隐藏 limitations。

## Slide 17: Takeaways (14:20--15:00)

The main conclusion is not that KV should always move. Routing addresses locality by reusing state where it already exists. Direct NVLink transfer provides fluidity when placement no longer matches known demand. The two mechanisms must cooperate, because copied KV has no service value unless routing directs requests to the replica. Finally, the rejection boundary is part of the result: memory pressure and request skew alone do not justify movement. In one sentence, route when possible and transfer when profitable. Thank you, and I welcome your questions.

讲解提示：最后回到两条 principle 和一句话结论，不再加入新信息。

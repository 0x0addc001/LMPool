# LMPool Oral QA

## 1. What is the complete path of a request through LMPool?

LLMEngine receives and tokenizes the request, then creates a Sequence. The
Sequence computes a chained prefix hash over complete prompt blocks; a partial
tail block is not globally reusable. The ingress ControlPlaneClient requests a
global route with requester rank $-1$, so the candidate set contains every
healthy GPU rather than only the NVLink partner of an initial GPU.

`requester_rank` identifies the GPU perspective from which routing starts; it
does not identify the final execution rank. When a request is already at a
worker, a nonnegative requester rank limits candidates to that worker and its
direct NVLink partner. A new request from LLMEngine has not been assigned to a
GPU, so $-1$ is a sentinel for "no local GPU." Global Scheduler therefore
considers every healthy replica with fresh published state and gives them the
same ingress topology weight. LLMEngine sends the Sequence to the selected
data-plane queue only after this decision. Rank $-1$ is not a physical rank and
does not participate in NCCL.

Global Scheduler obtains the contiguous ready-prefix length, queued and
running tokens, active sequences, free blocks, and dependency-safe reclaimable
capacity of every candidate from Global Block Manager. It computes route cost
and creates a temporary capacity reservation on the selected GPU. LLMEngine
then places the full Sequence in that data-plane process queue.

At the target, Local Scheduler asks Local Block Manager to increment reference
counts for reusable local blocks and allocate physical IDs for missing blocks.
Only a remaining real shortage can send foreground transfer to the cost and
feasibility gates. Model Runner executes prefill, writes missing KV, and then
decodes one token at a time. The worker returns first and final tokens, runtime
metrics, and a versioned block/load snapshot to LLMEngine and the control
plane. Completion releases references. Complete zero-reference prefixes remain
cached until reuse or dependency-safe reclamation.

In short, global metadata decides where the request runs, and the target
worker decides what can be reused or allocated locally. Only a real shortage
or an admitted predictive placement invokes transfer. KV tensors move between
Model Runners; the control plane handles only metadata and transaction phases.

## 2. Where are routing and transfer decisions made?

Global Scheduler in the control-plane process makes routing decisions from the
versioned prefix, load, and capacity snapshots in Global Block Manager. It also
plans transfer, but the two data-plane processes execute physical block
reservation, gather, send/receive, scatter, and publication.

Routing changes request placement. Transfer changes KV placement. The two
mechanisms share metadata and a cost view, but they do not replace each other.

## 3. Why can ingress routing consider all GPUs while transfer is restricted to an NVLink pair?

An ingress request does not yet have a source GPU, so routing can select the
healthy replica with the lowest projected cost. A physical transfer requires a
specific source and destination, and the current implementation supports only
configured or discovered direct NVLink pairs. Global routing therefore does
not imply arbitrary all-to-all GPU transfer.

## 4. Why must a prefix match be contiguous?

Attention for a later block depends on every preceding token. A later block
hash cannot safely resume a request when an earlier block in the chain is
missing. LMPool therefore counts only the longest ready chain that starts at
the first complete block.

## 5. What does route cost mean physically?

$Q_g$ is token-equivalent queued, pending, and running work on candidate GPU
$g$. $M_g$ estimates missing prefill tokens after rounding at block
boundaries. $A_gS$ represents capacity pressure that requires reclamation.
Global Scheduler minimizes

$$
C_{\mathrm{route}}(g)=Q_g+w_pM_g+w_eA_gS.
$$

This is not a reward that maximizes hit rate. Prefix reuse lowers the estimated
prefill work that must actually be executed.

## 6. Why is strict prefix-owner routing insufficient?

A hot prefix owner can receive too many requests. Sending every match to the
owner raises hit rate but can concentrate demand, reduce useful batching across
replicas, and increase queueing. LMPool permits bounded spill only when owner
load is clearly higher and extra recomputation remains within a configured
bound.

The extra recomputation is the additional missing-prefill and reclaim work on
the spill rank relative to the owner, combined with queue work on both ranks.
Transfer cost is not directly added to this spill route cost because "spill
this request and recompute now" and "copy KV first to serve future requests"
are different actions. Global Scheduler separately tests whether a
routing-guided copy is enabled and whether expected reuse repays measured
transfer cost. If that copy is not selected, direct spill is still allowed
within `owner_spill_max_extra_cost`. The paper configuration disables ordinary
routing-guided speculative copy: foreground transfer requires a real block
shortage, and background transfer requires the handoff forecast. Bounded spill
must therefore not be described as an implicit transfer.

## 7. What is the difference between foreground and background transfer?

Foreground transfer is demand-driven. When Local Scheduler observes a real
block shortage, it requests only the shortage, not every block of the
Sequence.

Background transfer is placement-driven. It copies a complete hot chain to a
GPU where future reuse is expected before the request arrives. Candidates must
still pass cooldown, pair-idleness, target-capacity, and benefit gates.

Both use the same transactional data path, but their benefit estimates differ.
Foreground transfer can use discounted historical reuse. Background transfer
counts at most the first avoidable cold prefill because a first miss would
naturally warm the destination.

## 8. What is the difference between copy and move?

Copy creates a destination replica while preserving the source. It is used
when source blocks remain referenced or both GPUs may reuse the prefix.

Move releases a dependency-safe, unreferenced source suffix only after the
destination has been published. A referenced block, or a block that is an
ancestor of another retained block, cannot be released by move.

## 9. Are KV blocks transferred between Block Manager objects? How is KV cache versioned?

No. Local Block Manager owns physical block IDs, reservations, references,
generations, and readiness. Source Model Runner gathers KV tensors, pair-local
NCCL sends them to destination Model Runner, and the destination scatters them
into reserved blocks. Block Manager then publishes the metadata.

LMPool does not attach one version number to the entire KV tensor. It uses four
identity and ordering layers. A chained prefix hash identifies logical
content. A physical block `generation` increments whenever a block ID is
allocated again; plans carry block ID, hash, and generation to prevent ABA
errors after release and reuse. A worker increments `state_version` for each
block/load snapshot, and the control plane rejects out-of-order snapshots that
are not newer than the accepted version. Finally, `worker_epoch` changes after
a worker restart and `control_epoch` changes after a control-plane restart.
Old page tables and messages become invalid after an epoch change, and routing
waits for a complete new snapshot.

The hash answers "which KV content is this?" Generation answers "is this
physical slot still the allocation observed by the plan?" State version
answers "is this snapshot newer?" Epoch answers "does this message belong to
the current process lifetime?"

## 10. How is the KV tensor packed?

For $B$ blocks, the packed tensor has shape

$$
[L,2,B,S,H_{kv},D],
$$

where the dimensions are layer, K/V, block, tokens per block, KV heads, and
head dimension. The source uses indexed gather to create one contiguous
tensor, NCCL sends one payload, and the destination uses indexed scatter.
Hashes, generations, and physical block IDs remain in the control protocol and
are not embedded in the tensor payload.

## 11. Why use prepare--execute--publish--finalize?

The key is the visibility boundary. Destination receive completion does not
mean the block is ready for routing. Prepare reserves resources. Execute moves
bytes. Publish exposes locally ready metadata to Global Block Manager.
Finalize decides whether to preserve or release the source. A failure before
publish cannot expose a partially completed replica.

The visibility boundary is the commit point where internal state changes from
unobservable to globally routable. In LMPool this point is publish, not return
from NCCL receive. After execute, the destination HBM may already contain the
correct bytes, but the block remains `transfer_pending_publish`. It does not
appear in the ready-block snapshot or the global routable page table. Publish
registers the block, sets `kv_ready`, clears pending state, and reports a newer
snapshot. The replica becomes a route hit only after the control plane accepts
that snapshot. This prevents a request from observing bytes whose metadata,
parent chain, or capacity state has not committed.

## 12. Is concurrent access safe?

Each worker serializes block mutations in a single-threaded event loop. The
control plane likewise serializes state mutation in one event loop. A
per-client receive lock prevents multiple callers from consuming the same
response queue. Worker snapshots carry epoch and version information, so stale
updates are rejected. Transfer phases are idempotent by plan ID and phase.

This is not distributed consensus. Launcher failure stops service, and worker
failure loses the physical cache of that worker.

## 13. What exactly is the fixed 40 ms term?

The final paper transfer workload sets
`--foreground-transfer-fixed-latency-ms 40.0`. This is not a fitted residual
from an independently reproducible Qwen3-0.6B pilot. It is a manually selected
conservative cold-start prior for coordination, NCCL queueing, destination
publication, block registration, and other costs omitted by an idle
microbenchmark.

Payload-dependent cost comes from measured P95 profiles for each direct pair.
At runtime, source and dispatch-to-publish observations update separate
nonnegative EWMAs by pair and size bucket. Admission takes the maximum of the
static prior and the available online estimates. The paper explicitly lists
the missing 40 ms sensitivity study and held-out prediction error as
limitations.

For a plan, the model first computes payload bytes and obtains
$T_{\mathrm{data}}$ from the 1/2/4/8/16/32/64-block P95 curve of that pair. The
static cold-start estimate is

$$
T_{\mathrm{static}}=40\text{ ms}+1.2T_{\mathrm{data}}.
$$

A successful source operation records gather, P2P, and related source-path
time. The nonnegative difference between that observation and profiled
data-path time updates the source residual EWMA for the pair and
power-of-two size bucket. A complete plan records
dispatch-to-destination-commit time. Its nonnegative residual over the static
estimate updates a
separate placement EWMA for the same pair and bucket. EWMA smooths transient
noise, and clamping residuals to zero prevents one unusually fast sample from
making admission more aggressive than the offline P95 prior.

Admission uses

$$
T_{\mathrm{xfer}}=\max(T_{\mathrm{static}},T_{\mathrm{source}},T_{\mathrm{placement}})
$$

to select the most conservative available estimate without adding overlapping
measurements. A plan proceeds only if
$T_{\mathrm{save}}\geq\rho T_{\mathrm{xfer}}$ and source generation, direct-pair
topology, target capacity, and other validity conditions still hold.

Missing 40 ms sensitivity means that the paper has not systematically compared
plan acceptance, throughput, and latency at, for example, 0/10/20/40/60 ms.
Missing held-out prediction error means that one set of runs has not been used
to calibrate profile/EWMA state and a disjoint set to report predicted versus
observed MAE, P95 error, and underprediction rate. The multi-size data path is
measured, but the fixed intercept and complete serving-cost predictor still
lack independent validation.

## 14. Why is microbenchmark bandwidth alone insufficient for transfer admission?

The microbenchmark measures a relatively idle data path. Serving adds
scheduler coordination, target reservation, interference with model kernels,
publication, and block registration. Estimating cost as payload bytes divided
by bandwidth would systematically underestimate complete short-plan
transactions.

## 15. Why measure 1/2/4/8/16/32/64 blocks?

These powers of two cover small foreground plans through large coalesced
background plans with few measurements and align with runtime size buckets.
They reduce the 1-to-64 range from 64 integer experiments to seven calibration
points while making fixed-cost amortization visible as payload doubles.
Runtime EWMA assigns a real plan to the next power-of-two bucket; for example,
5--8 blocks share the 8-block bucket so each bucket accumulates enough samples.

Latency lookup and EWMA bucketing are separate. A plan between two measured
points, such as six blocks, uses piecewise-linear interpolation by payload
bytes between the four- and eight-block points. A plan smaller than the first
point uses the first measured latency conservatively. A plan above the largest
point uses a nonnegative linear extrapolation from the final 32- and 64-block
segment. Only if that segment has zero slope does the implementation fall back
to the average slope of the last point, `last_ms / last_bytes`. The final
implementation therefore uses the last-segment slope beyond 64 blocks rather
than clamping latency at the boundary.

## 16. Is four-block bandwidth the fixed online batch size?

No. Four blocks is one calibration point. Foreground plan size follows the
real shortage. Background placement may coalesce several chains on the same
directed pair. The paper no longer uses one four-block bandwidth value for
every plan.

## 17. Why is block size 256 when vLLM often uses smaller blocks?

The Mini-vLLM prototype and paper workloads fix block size at 256 tokens. This
creates a sufficiently large complete transfer unit and reduces metadata
count, but it can increase tail waste and fragmentation and changes transfer
amortization. The paper does not claim that 256 is optimal. Sensitivity at
16/64/256 tokens is future work, so the current results should not be
extrapolated to other page sizes.

## 18. Does transfer affect routing? Does routing affect transfer?

(1) Yes, by design. After destination publication, Global Block Manager records a
new replica. A placement lease gives source and destination request quotas so
routing can use the copied KV. The replica is invisible before publication.
Without a lease, ordinary cost-based routing may still choose it.

A placement lease is neither a GPU memory lock nor permanent KV ownership
transfer. It is a short-lived control-plane routing quota created for a prefix
leaf after successful forecast-driven background copy. It stores source GPU,
replica GPU, remaining request quota on each side, the next preferred side,
and the NVLink pair. A matching request consumes alternating source/replica
quota before ordinary route-cost evaluation, while still checking that the
target has a contiguous ready chain and valid capacity. The lease is removed
when quotas are exhausted.

The lease solves the "copy succeeded but demand stayed at the original owner"
problem. Transfer changes the visible replica set; the lease spreads known
forecast demand across source and destination so that the replica becomes
parallel serving capacity.

(2) Yes. Routing changes prefix accesses, queue pressure, free capacity, and
replica distribution on every rank. Those states determine transfer candidate
chains, source/destination choice, and expected benefit. If routing already
sends demand to a reusable owner whose load is acceptable, transfer is
unnecessary. Transfer becomes relevant when a forecast places future demand at
a partner or a real shortage occurs. An ordinary route hit or bounded spill
does not unconditionally trigger transfer. In the paper configuration,
foreground transfer is shortage-driven, while positive background transfer is
driven by the benchmark handoff forecast.

## 19. Why can transfer-only have a high cached-token ratio without higher throughput?

In session handoff, transfer-only and full LMPool both reach a 70.5%
cached-token ratio, but transfer-only retains a rank request ratio of 3.3 and
mean GPU
utilization of only about 31--33%. It removes cold prefill without sending
demand to the new replica. Placement-lease routing in full LMPool lowers the
request ratio to 1.8 and raises mean GPU utilization to about 50--52%, which
turns the copy into throughput.

Rank request ratio is the maximum submitted request count over the minimum
nonzero submitted request count across ranks in one scenario. A value of 1
means equal request counts. A value of 3.3 means the busiest rank receives
about 3.3 times as many requests as the least busy nonempty rank. It measures
request-placement skew, not TP, DP, or model parallelism. Request counts alone
can hide different sequence lengths, so the paper also checks per-rank tokens,
execution time, and GPU utilization.

## 20. Why is routing-only sometimes as good as full LMPool?

When routing can already send a request to a prefix owner without overloading
that owner, transfer has little incremental opportunity. In the Qwen3-0.6B
session-handoff result, the 95% confidence intervals of mean E2E for
routing-only and full LMPool overlap. The paper therefore presents stronger
incremental evidence for throughput and the more compute-intensive model, not
a claim that transfer improves every metric beyond routing-only.

## 21. Why does the load-skew workload not show a transfer advantage?

Round robin distributes the 144 hot requests across six workers, so each
worker naturally caches the same hot prefix early. Baseline cached-token ratio
is already about 85.9%, and each rank receives exactly 32 requests. KV
placement is already sufficiently replicated, leaving no additional work for
routing or transfer to eliminate.

## 22. Why does the memory-skew workload also show no advantage?

Memory pressure is necessary but not sufficient. The source must have a
complete safely movable or copyable reusable chain, the destination must have
capacity, and future reuse must repay the transaction. The Qwen3-1.7B
memory-skew cost gate admits no transfer, so this result validates a rejection
boundary rather than transfer speedup.

The rejection boundary is the set of conditions that separates "accept
transfer" from "reject and continue locally," not one scalar threshold. It
includes a complete source chain with valid generations, a direct NVLink pair,
an idle pair, reservable target capacity, no duplicate or cooled-down
candidate, and saved prefill above the safety ratio times conservative transfer
cost. Failure of any gate puts the plan on the rejection side. Memory pressure
alone does not cross this boundary; reusable KV, feasible placement, and enough
future demand must coincide.

## 23. Does session handoff use an oracle?

It uses exact queued-request demand supplied by the benchmark, which is a
controlled accurate forecast rather than an evaluated online predictor. The
workload isolates whether placement, transactions, and lease routing produce a
benefit when an opportunity is known. Online prediction precision, recall,
lead time, and invalid-copy rate remain future work.

An oracle supplies information that a live system normally cannot know
perfectly in advance. The benchmark has already generated every reuse-phase
prompt, so it can count exactly how often each prefix appears in the next 96
queued requests and submit those counts at the phase boundary. This perfect
demand oracle answers "can the mechanisms realize a benefit if future demand
is known?" It does not answer "can an online predictor forecast that demand?"

Lease routing is the short-lived quota policy used after an oracle/forecast
copy succeeds. The control plane allocates future-demand quotas to source and
destination and alternates matching requests while revalidating prefix
readiness and capacity. Unlike ordinary minimum-cost routing, the lease
explicitly consumes known demand on the new replica and expires when the quota
is exhausted.

## 24. How does LMPool differ from vLLM or SGLang?

vLLM PagedAttention and SGLang RadixAttention mainly manage allocation and
prefix reuse inside one engine. LMPool studies admission-time placement across
data-parallel replicas with independent allocators. Global routing selects the
replica, and cost-gated transfer copies or moves complete prefix chains across
a direct NVLink pair.

The paper does not contain production-grade vLLM or SGLang end-to-end
baselines, so it does not claim overall superiority over those systems. Its
contribution is a mechanism study with controlled evidence, not a production
system SOTA claim.

## 25. How does LMPool differ from Mooncake, LMCache, or PegaFlow?

Those systems primarily provide cross-instance, cross-node, or cross-tier KV
visibility and persistent capacity, often through RDMA, host DRAM, or SSD.
LMPool focuses on peer HBM in a scale-up server and combines request routing,
load/capacity state, and measured pair-local transfer cost in one admission
view.

The approaches can be complementary. Remote or persistent cache provides
capacity and cross-node reuse; LMPool principles can decide whether to route
locally, transfer over an NVLink peer, or fall back to a more distant tier.

An admission decision is the gate taken before an expensive operation begins.
For routing it selects a rank with valid capacity and reserves that capacity.
For transfer it checks source identity, topology, target space, pair
availability, and benefit/cost, then admits, defers, or rejects the plan. One
control plane does not mean one formula performs both actions. It means route
placement and KV placement read the same versioned locality, load, capacity,
and cost state, so one component does not create a decision that the other
cannot fulfill.

## 26. How does LMPool differ from Aqua?

Aqua targets burst memory pressure and paging of active inference state into
idle HBM on other GPUs to reduce preemption cost. LMPool uses content-addressed
complete prefix chains for future prefix reuse and couples copy placement with
request routing. Their triggers and objectives differ.

## 27. Why evaluate only Qwen3-0.6B and Qwen3-1.7B?

Both models fit as complete data-parallel replicas on six 24 GiB RTX 3090 GPUs
and permit repeated trials. They share KV geometry, so a transfer has the same
payload and the main difference is compute intensity. This isolates the
mechanism but does not establish generality for larger models, different
GQA/MLA layouts, or different KV bytes per token.

The current results generally make avoided prefill more valuable for
Qwen3-1.7B. In routing, both models raise cached-token ratio from about 44% to
about 72%, but mean TTFT rises by 7.4% for Qwen3-0.6B and falls by 10.2% for
Qwen3-1.7B. In session handoff, full LMPool improves throughput by 4.4% and
7.4%, lowers TTFT by 32.4% and 40.4%, and lowers E2E by 9.3% and 12.9% for
0.6B and 1.7B, respectively. The same KV payload avoids more compute on the
1.7B model, increasing the saved-compute-to-transfer-cost ratio.

This does not imply that a larger model always benefits more. Model size can
change KV heads, head dimension, dtype, available HBM, parallelism strategy,
and communication/kernel interference. If KV bytes grow faster than avoidable
compute, or the model requires tensor parallelism rather than independent DP
replicas, transfer may become more expensive. The relevant quantity is saved
prefill time divided by the full transfer, queueing, and interference cost, not
parameter count alone. More model families would strengthen external validity
but would not automatically improve the measured gain.

## 28. Why are production traces and production baselines absent?

The current work prioritizes controlled workloads that separate routing,
transfer, memory pressure, and naturally replicated locality. This improves
mechanism isolation at the cost of external validity. The paper explicitly
describes a prototype mechanism study. Public multi-turn traces, online
forecasting, and production-engine baselines under equal KV budgets are next
steps.

## 29. Is higher GPU utilization always better?

No. Higher utilization is useful only when throughput, latency, and goodput
also improve. In session handoff, LMPool raises utilization from about 32--35%
to 50--52% while improving throughput and latency, which indicates more useful
load distribution. Higher utilization with worse latency could instead mean
congestion.

GPU memory utilization is also not a metric to maximize in isolation. Too low
means idle capacity; too high raises admission failures, reclamation, and
preemption risk. The paper fixes a per-worker KV budget for fair baselines.

## 30. What do route hit, owner hit, local hit, and cached tokens mean?

Route hit means the control plane found at least one matching prefix when it
routed the request. Owner hit means the selected destination was one of the
recorded owners at that time. Local request hit means initial prefill at the
data plane reused at least one local ready block. Cached-token ratio is the
number of reused prompt tokens divided by all prompt tokens.

The first three are binary request-level rates. Cached-token ratio is a
token-weighted estimate of reduced work. Reusing one block and seven blocks
both count as one local request hit, so the paper primarily uses cached tokens
and uncached tokens to explain compute savings.

## 31. Can KV cache from one scenario affect the next scenario?

No. Each scenario and trial creates new worker processes, Model Runners, and
Local Block Managers. GPU KV cache disappears when those processes exit.
Runtime prefix state is not shared across results. Model files can remain in
the operating-system or Hugging Face file cache, but request timing begins
after worker initialization and model warm-up.

Model warm-up runs a small synthetic prefill/decode before formal serving
timing to initialize the CUDA context, weights, KV allocation, kernel path, and
NCCL communicator. It differs from the warm-up phase of session handoff. That
workload phase is part of the measured scenario: the first 32 requests are
pinned to the source sides of the NVLink pairs to create one complete long
prefix for each of 32 groups. The benchmark waits for all 32 to finish, then
performs background placement and starts the 96-request reuse phase.

## 32. Is the control plane a single point of failure?

Yes, in the current implementation. LLMEngine can monitor and restart the
control-plane process, and worker snapshots can rebuild global metadata, but
this is not consensus or high availability. Launcher failure stops service.
A production version would need replicated metadata, leader election, and
launcher failover.

## 33. What was the most difficult engineering problem?

The hardest problem was making "bytes have arrived" consistent with "metadata
allows routing to those bytes." Early failures included premature destination
visibility, release of referenced source blocks, double free from repeated
phases, and hangs caused by P2P ordering or rendezvous. The solution was not a
global lock. It was single ownership, generation/version checks, a
prepare--publish visibility boundary, idempotent plan phases, abort rollback,
and failure/concurrency tests.

P2P ordering requires source and destination to enter matching NCCL send/recv
operations with the same pair, tensor shape, direction, and order. If one rank
waits on plan A while its peer starts plan B, or one side sends without the
matching receive, both can wait indefinitely. Rendezvous requires every rank
in process-group initialization to use the same store/init method, world size,
and unique available endpoint. A stale process holding the port causes
`EADDRINUSE`; a missing rank, mismatched world size, or mismatched endpoint can
cause an indefinite wait.

A Python global lock serializes only participants that acquire that same lock.
It cannot automatically match NCCL calls across independent worker processes,
and it cannot prove that a block was not released and reused while waiting.
Serializing all routing, allocation, and transfer would also damage concurrency
and throughput. LMPool instead uses narrower protocol rules. Local Block
Manager is the sole owner of physical blocks. Hash plus generation prevents
ABA. Worker snapshot version and epoch reject stale state. Prepare pins the
source and reserves the target. Publish is the only visibility boundary.
Replaying the same `(plan_id, phase)` returns the cached result without a
second mutation. Failure aborts the transaction, preserves the source, and
releases the destination reservation. Tests inject repeated phases, stale
generations, failed publication, process restarts, and concurrent response
consumption rather than testing only the successful path.

## 34. What did you learn from developing this project?

First, reducing unnecessary data movement should precede optimizing the data
path, so routing and transfer form one cost decision rather than two unrelated
features. Second, cache hit rate is not the objective; uncached work, queueing,
rank distribution, throughput, and latency must be observed together. Third,
performance mechanisms in a distributed GPU system require explicit data
ownership and publication semantics. A successful NCCL receive alone does not
guarantee a correct globally visible state.

Uncached work is prompt prefill that the target worker must still execute
because no contiguous ready KV is reusable, including token computation and
the associated block allocation. The paper uses uncached prompt tokens and
prefill time to approximate this work. Publication semantics define who may
observe a state change and under which conditions. Destination bytes become
globally routable only after block registration, `kv_ready`, parent-chain and
generation validation, and a committed new snapshot. Source blocks can be
finalized or reclaimed only after destination publication. These semantics
separate successful byte movement from safe system state.

More broadly, the project developed the ability to reason about tradeoffs with
measured costs: locality versus load distribution, transfer versus
recomputation, large-block batching efficiency versus internal fragmentation,
conservative admission safety versus missed opportunities, strong consistency
protections versus control overhead, centralized metadata simplicity versus
availability, and mechanism isolation with an exact forecast versus production
realism. System optimization is not maximizing one metric. It is defining the
correctness boundary first, then using workloads, a cost model, ablations, and
negative results to decide which side of each tradeoff is preferable.

## 35. If you could add only one experiment, what would it be?

The highest-priority experiment would jointly validate the cost model and
forecast on a public multi-turn trace. An online demand estimator would record
predicted cost, observed cost, and realized future reuse for every candidate
plan. The evaluation should report forecast precision/recall, invalid-copy
rate, cost MAE and P95 error, and throughput/TTFT for no-transfer,
always-transfer, profile-only, and profile-plus-EWMA policies. This directly
tests whether the system discovers and selects profitable transfers under
unknown traffic.

A forecast estimates at least four properties: which prefix chain will be
reused, how many times it will be reused, which rank or NVLink pair will receive
that demand, and how much lead time remains before first reuse. Background
transfer must be early enough to finish before arrival and accurate enough to
avoid unused copies. The current session-handoff benchmark supplies exact
future-prefix counts and therefore validates the placement opportunity when
the forecast is correct. A production version must estimate demand from
session identity, prior prefix accesses, route hits, arrival patterns, or
application hints, then report precision, recall, lead time, invalid-copy rate,
and the throughput/latency effect of incorrect forecasts.
